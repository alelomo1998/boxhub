# M14 — the coach programming tour

**Date:** 2026-08-09 · **Status:** tour complete, decisions taken, spec not yet written

This is the tour the v2 roadmap said M14 could not be specced without: *"Before M14 is specced, the
coach programming screens need an actual tour. They were skipped as 'part 2', then split, and the
half pulled into M14 has never been reviewed. Its scope currently rests on inference and stale
backlog entries."*

It is **not** the spec. It is the raw observations, what was verified against the code, and the
decisions taken — so the spec can be written from evidence rather than memory.

---

## 1. What the user said, kept close to verbatim

**Classes page** — "not wrong but not ok". Will keep the same styles as the athlete booking rework,
since it is a similar page. Athletes only book; coaches do their actions.

**Builder** — not ok:
- **Blocks of blocks.** Define a block (e.g. warmup) and inside it put other blocks with the single
  exercises.
- **Mobile reorder must be swipe**, not the current arrows.
- **The big categories must be macros** — warmup, strength, gymnastic, workout. **AMRAP, Tabata,
  EMOM are subcategories** and indicate the type of the WOD.
- **A real system to build EMOM and Tabata.** "we can have an emom that can be 2 minutes on 1 off
  2 on on another thing so we need a good system to create it." Later, decisively: *"we need another
  block structure i think… a simple one: every minute 20 squat, or a complex one every 30 second
  squat, then 15 second rest then 30 second burpees, but maybe is a tabata. we need the creation to
  be dynamic and not to bounded."*
- **Team WODs** exist and have to be managed.
- **The scored checkbox is horrible** — needs a check item suited to the job.

**Build page** — "orrible":
- Remove the **duplicate** function.
- Checking a WOD / creating a new one should use the same page as building a class — **or** split
  into two pages, build a class and build a block, so a single block can be made and then attached.
- "lets assume we have the standard schedule every week, the class is empty of exercise, then we can
  build it? idk maybe im reading it wrong take a look."

**Admin** must be able to see the classes, the exercises, everything.

**Coach** must see **all** classes, including other coaches'. Better surfaced in the table. **A coach
can run another coach's class, and that must be tracked** — for analytics.

**Types page** — "not a coach matter but an admin matter no? we are permitting our workers to change
the structure of the classes? i dont think so."

**Benchmarks page** — probably useless. Maybe a tab to check all past WODs and blocks of exercises.
Not only coach-relevant.

**All of these pages**: not mobile friendly, no back arrows, some text really small, some buttons too.

## 2. What the code actually says — verified, not inferred

**The user's reading of the class model was RIGHT.** The chain he described already exists:

| Entity | What it is |
|---|---|
| `TemplatePiece` | a skeleton slot on a class **type** — label + `wod_type` only. Its own javadoc: *"Skeleton placeholder on a class type… Pre-seeds the builder."* |
| `ClassSession` | the weekly instance of that type |
| `SessionItem` | a `Wod` attached to a session, with `sort_order`, `scoreable`, optional `score_type` |
| `Wod` | reusable programming: `title`, `wod_type`, `score_type`, `time_cap_seconds`, `body_text`, `blocks_json` |

So *standard schedule → empty labelled slots → coach fills them* is the model, exactly as he guessed.
**The UI hides it** behind two builder pages that never say which is which.

**The category complaint is a schema bug, not a UI one.** `PieceTypes.ALL` is one flat list mixing
two axes:

```
FOR_TIME, AMRAP, EMOM, INTERVAL   ← timing schemes (how it runs)
STRENGTH, WARMUP, CIRCUIT, SKILL  ← section kinds (what part of class)
CUSTOM                            ← neither
```

**There is no TABATA in the vocabulary at all.**

**Blocks are one level deep.** `WodJson`: `Blocks → Block{label, note, lines[]}` → `Line{text,
movementId, reps, load, scaling}`. No nesting.

**Interval structure does not exist.** The only timing field on a `Wod` is `time_cap_seconds`.

**The timer is already server-authoritative and is bounded to two shapes.** `runner.page.ts:305
buildSpec()` emits either `{type, totalSeconds}` or `{type, rounds, workSeconds, restSeconds}` —
**uniform rounds only**, so the user's "30s squat / 15s rest / 30s burpees" cannot be armed. Two
things make this cheaper than it looks: `ClassTimer.spec_json` is a free-form text column, so a
richer spec needs **no migration**; and today the coach **re-types** rounds/work/rest into the runner
by hand — the programming and the clock do not talk to each other.

**No team concept exists** anywhere in the backend domain.

## 3. Decisions taken during the tour

| # | Decision |
|---|---|
| 1 | **A piece has three axes: macro + timing + score.** Score is set explicitly, not derived — so a WORKOUT/AMRAP scored by load is expressible without a special case. |
| 2 | **Block nesting is exactly two levels.** Macro block → exercise blocks. Fixed depth. |
| 3 | **One builder page**, same UI for checking a WOD, creating one, and building a class. |
| 4 | **A block is local to its class unless explicitly saved to the library. Default off.** Re-saving an edited local block updates in place. This is the fix for the filed unbounded-`wod`-growth bug, which exists precisely because one page did both jobs implicitly. |
| 5 | **Types page becomes admin-only.** Class types define the box's structure; coaches program inside it. Moves out of M14's coach set. |
| 6 | **Benchmarks page is deleted.** The WOD library gains a history tab covering past WODs and reusable blocks; benchmarks become library entries flagged as such. |
| 7 | **Timing becomes a segment sequence**, and a segment is `(duration, kind: work/rest, optional movement/label)`. |
| 8 | **AMRAP / EMOM / Tabata / For time become presets over that sequence, not types.** The preset name survives for filtering, analytics and the board's eyebrow, but never constrains what can be built — "dynamic and not bounded", while keeping the vocabulary athletes actually speak. |
| 9 | **The runner auto-arms its timer from the programmed piece, with a coach override.** Kills the double entry. The override is required — classes run late and coaches shorten pieces. |
| 10 | **Team WODs are scoped in M14, designed at the screen.** Deliberately not modelled against no screen — that is how `bh-stat` happened. |

### What decision 8 buys, concretely

```
EMOM 12   →  12 × [ 60s work ]
Tabata    →   8 × [ 20s work, 10s rest ]
the user's →  N × [ 30s work "squat", 15s rest, 30s work "burpees" ]
AMRAP 20  →   1 × [ 20:00 work ]
For time  →   1 × [ cap ]
```

One structure. The preset is a starting point the coach edits freely.

## 4. Still open — to be asked at the screen, not guessed

Per the standing rule (never guess a UI decision; ask), these are recorded rather than resolved:

- **Coach visibility of other coaches' classes**, and **tracking who actually ran a class** versus
  who was assigned it — the user asked for both, explicitly for analytics. Is "ran by" a new field
  distinct from the assigned coach, and does it need to survive a swap mid-class?
- **Admin sees everything** — which screens does that mean, and read-only or editable?
- **The scored checkbox replacement** — what the check item should actually be.
- **Mobile reorder by swipe** — for both levels of block, or only exercises within a block?
- **Team WOD depth** — score-entry only, or roster split (which overlaps "Heats/teams", filed under
  Project 2).
- **Mobile basics across all these pages** — back affordance, type sizes, tap targets. M13c's
  components fix the primitives; the screens still need their own pass.

---

## 5. How M14 gets built

Binding, stated by the user at the start of this tour: **screen by screen, page by page, component
by component — one tab at a time.** Hours are explicitly not the constraint; building the whole thing
wrong is. Each screen is shaped, asked about, built and reviewed before the next is started, and its
open questions are asked rather than assumed.
